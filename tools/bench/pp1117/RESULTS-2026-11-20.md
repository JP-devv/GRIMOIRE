# GRIMOIRE v1.10.10 benchmark results

Measurements use the v1.10.10 image built from `acc75ea3d74cbedfc3f2857a96787409be88dd0e` on Intel Arc Pro B70. The image includes G31 and G21 device code.

**Reading the tables.** Prefill measures how fast the model reads the prompt. Decode measures how fast it writes the answer. Both use tokens per second. TTFT is the time until the first output token. A prompt length is the number of input tokens the benchmark requests. The configured context limit is how many tokens the server can hold per sequence, including the output.

**Which switches matter.** Radiance placement is Grimoire’s implementation of Radiance’s expert-placement policy for Flash-Next. Dense Qwen3.8-27B has no routed experts. KV pooling is new in v1.10.10. It is opt-in with `GRIMOIRE_KV_POOL=1` on supported single-GPU configurations. All two-B70 runs here use fixed KV slots.

## Two B70s, INT8, before and after

The comparison uses the released v1.10.9 as the before-work image. The matched runs use the same model files, GPU settings, MTP options and prompt text on both versions. The harness seeds llama-benchy’s prompt generator and unique suffixes and verifies the generated prompts by SHA-256 before reporting the pair. Each test requests up to 128 generated tokens with one active request.

**Flash-Next** write speed rose by 1.4–3.6%. Reading rose by 28–31% at 4K and 16K on this pass and remained about the same at 32K and 64K. The short-prompt reading measurements are from one run order. PLE file-cache warmth can affect the difference. The Flash-Next model uses NVFP4 expert weights with INT8 projections and a 69,632-token limit to fit the full 65,536-token prompt and output. [Historical v1.10.9 results](RESULTS-2026-11-19.md)

## What KV pooling changed

This completed capacity test used **Swift Qwen3.8-27B INT4 with MTP K6**, one B70, eight simultaneous client requests, a 131,072-token configured context limit, and 128 output tokens per request. Radiance placement did not apply. The paired before/after runs kept the workload and configuration the same and changed KV allocation.

| Workload | Input per request | Fixed KV active slots | Pooled KV active slots | Fixed total output | Pooled total output | Gain |
|---|---:|---:|---:|---:|---:|---:|
| Code | 60 tokens | 2 | 8 | 153 tok/s | 315 tok/s | 2.06× |
| Essay | 49 tokens | 2 | 8 | 124 tok/s | 284 tok/s | 2.29× |

The old fixed layout reserved memory for 128K tokens per slot. It fit two active slots, so six requests waited. Pooling allocated memory for each short request as needed and ran eight together. The throughput figures include the time spent waiting and reading the prompts. In a separate single-user paired test, decode changed by −0.06%. The long-context probe later passed through 128K tokens on both B70s after the fix. [Capacity A/B details](../../../HANDOFF-2026-11-19.md#resume-results)

The **INT8 deployment** comparison used the final v1.10.10 image, Qwen3.8-27B Uncensored with INT8 projections and MTP K6, one B70, a 24,576-token context limit, and 512 input / 128 requested output tokens. Both runs use a 0.75 GiB VRAM reserve. The explicit reserve keeps the fixed baseline in GPU memory. Pooling is the only variable changed. The fixed layout fit one active slot. The pooled layout offered eight slots with a 1.08 GiB shared budget. Both completed all 26 measured requests with identical prompts across settings. Total throughput includes time spent in the queue and reading the prompt. Radiance placement does not apply to this model.

| Simultaneous requests | Fixed KV aggregate tok/s | Pooled KV aggregate tok/s | Fixed median TTFT | Pooled median TTFT |
|---:|---:|---:|---:|---:|
| 1 | 62.8 | 62.0 | 0.320 s | 0.347 s |
| 4 | 59.9 | 115.2 | 3.512 s | 1.442 s |
| 8 | 55.3 | 150.7 | 8.399 s | 2.897 s |

At eight requests, pooling delivered **2.73× the total output** and cut median time to the first token by **66%**. With one request, total throughput was about 1% lower. This is primarily a concurrency and memory-capacity improvement.

## What Radiance placement changed

Both sides ran the final v1.10.10 image with Flash-Next INT8 projections, the same inputs, MTP off, and 128 generated tokens. The one-B70 runs used pooling in both modes and two repeats per prompt length. The two-B70 runs used fixed KV in both modes and one repeat per prompt length. The configured context limit was 69,632. The only feature changed within each pair was Radiance expert placement.

| B70s | Prompt | Heat off, read / write | Heat on, read / write | Write change | Full response off → on |
|---:|---:|---:|---:|---:|---:|
| 1 | 4,096 | 875.1 / 34.22 | 888.0 / 40.81 | +19.3% | 8.47 → 7.80 s |
| 1 | 16,384 | 1,110.5 / 33.23 | 1,170.8 / 40.21 | +21.0% | 18.74 → 17.27 s |
| 1 | 32,768 | 1,034.3 / 32.57 | 1,023.3 / 39.13 | +20.1% | 35.83 → 35.50 s |
| 2 | 4,096 | 1,583.2 / 50.07 | 1,441.1 / 51.61 | +3.1% | 5.17 → 5.35 s |
| 2 | 16,384 | 1,769.9 / 49.79 | 1,450.2 / 52.03 | +4.5% | 11.85 → 13.78 s |
| 2 | 32,768 | 1,646.9 / 48.71 | 1,654.1 / 49.72 | +2.1% | 22.56 → 22.41 s |
| 2 | 65,536 | 1,460.9 / 48.29 | 1,464.7 / 47.19 | -2.3% | 47.54 → 47.48 s |

With **one B70**, Radiance placement improved write speed by 19–21% at all three lengths. The full response was about 8% faster at 4K and 16K and 1% faster at 32K, where reading the longer prompt takes most of the time. The single-card default stays enabled when sufficient pinned RAM is available.

With **two B70s**, the 4K and 16K responses took longer with placement enabled. The 32K and 64K response times were close. Placement stays off by default on two cards. The B70 links recorded for these benchmarks were Gen4 x8 and Gen4 x4.

The earlier one-board INT4 test rose from 44.9 to 52.8 tok/s at a 512-token prompt. The per-expert width split across the two GPUs remains pending. ## Flash-Next MTP verification

Two B70s, Flash-Next INT8 projections, MTP K3, fixed KV and Radiance placement off. The two images received identical 512-token prompts with 512 output tokens requested, two repeats each.

| Image | Prefill tok/s | Decode tok/s | Timed speculative steps |
|---|---:|---:|---:|
| v1.10.9 | 577.3 | 48.36 | 42.4–43.4 ms |
| v1.10.10 | 523.0 | 58.11 | 38.6–39.6 ms |

Decode improved by **20.2%** on this workload, while prefill throughput fell **9.4%**. The timing range excludes the short startup sanity request.

## Validation status

- The suite skipped 21 cases whose checkpoints were unavailable on the test machine.
- The original candidate failed with a Level Zero mapping error at long pooled prompts. The fix keeps physical extents below 2 MiB when using ordinary pages. The standalone probe now passes growth to 128K on both B70s.
- Flash-Next now keeps the pooled VRAM budget available for KV pages while the heat policy can still move experts among the existing slots.
- The final build’s CLI matched v1.10.9 in all 23 runnable cases. The CLI executable and kernel libraries match the packaged image by SHA-256. The repaired server completed real pooled 4K and 16K requests on one B70. The matched speed tests are complete. The matched MTP run, the final Flash-Next copy test, and the fresh single-card pooled 128K run passed. The archive checksum and Docker load passed.

## Experimental exchange options

`GRIMOIRE_TP_PLE_RAW=1` exchanges raw PLE rows in Flash-Next TP2 plain decode. `GRIMOIRE_PLE_READ_POOL=1` reuses workers for single-row PLE lookups. Both default to off. Across three runs per workload, the changes reproduced all 18 compared outputs, with median decode within 0.6% of the baseline.
